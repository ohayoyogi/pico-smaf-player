# RP2040 への移植：資源の見積もり

このリポジトリは、Yamaha MA 系 FM 音源チップの音色を再現する SMAF プレイヤー（上流：akustikrausch/yamaha-smaf-player）を、RP2040 で動く音源モジュールに移植するための作業場所です。
この文書は、上流のコードをそのまま RP2040 に載せた場合の資源を測り、書き換えが必要な箇所を示します。

## 測定条件

- 対象：上流の初期コミット `627f7ad`（2026-09-29 に測定）
- コンパイラ：arm-none-eabi-g++ 9.2.1。`-std=c++2a -Os -mthumb -fno-exceptions -fno-rtti`
- 各 `.cpp` をオブジェクトにして `arm-none-eabi-size` で測った。リンクはしていない
- CPU の指定は Cortex-M0+（RP2040）と Cortex-M33（RP2350）の 2 通り

## コードサイズ（実測）

| ファイル | RP2040 の text（バイト） | RP2350 の text（バイト） |
|---|---|---|
| `ma_player.cpp` | 11,812 | 11,296 |
| `ma_fm_core.cpp` | 4,534 | 4,620 |
| `smaf_file.cpp` | 3,674 | 3,626 |
| `smaf_voice.cpp` | 1,236 | 1,292 |
| 合計 | 21,256 | 20,834 |

この合計には、次のものが入っていません。

- `sin`、`pow`、`log2`、`floor` などの数学関数（倍精度版）
- 倍精度の演算を実現するソフトウェア実装（`__aeabi_dadd`、`__aeabi_dmul` など）
- `std::vector`、`std::string`、`new` を支える C++ 標準ライブラリ

これらはリンクして初めて分かるので、未測定です。

## RAM（実測）

ホスト上で `sizeof` を測った値です。

| 項目 | バイト |
|---|---|
| `MaPlayer` 本体 | 35,040 |
| うち FM ボイス（816 バイト × 32 個） | 26,112 |
| うちチャンネル状態（48 バイト × 128 個） | 6,144 |
| うち PCM ボイス（144 バイト × 16 個） | 2,304 |
| `ma_fm_core.cpp` の静的領域（BSS） | 11,536 |

上の他に、曲ごとに大きさが変わる領域が 2 つあります。

- イベント列 `events_`：1 件 16 バイトで、曲を読み込むときに全イベントを展開する
- 波形バンク `waveBank_`：ADPCM を展開した PCM 波形

RP2040 の RAM は 264KB です。
固定部分（約 47KB）は収まります。
ただし、イベント列を全展開する方式は、曲が長いと足りなくなる可能性があります。

## 演算（読んだ範囲での見立て）

この項は実行して測った値ではなく、コードを読んだ結果です。

FM 音源の 1 サンプルごとの処理（`ma_fm_core.cpp` の `FmOperator::waveform_` と `tick`）は、倍精度（`double`）で書かれています。
波形の生成には、オペレータごとに `std::sin` を呼びます。
RP2040 には浮動小数点演算ユニットが無いので、倍精度の演算と `sin` はすべてソフトウェアで実行されます。

出力を 22,050 Hz とすると、1 サンプルに使える時間は 125〜133 MHz で約 6,000 サイクルです。
ソフトウェアの倍精度 `sin` は、1 回で数千サイクルかかる見込みです（未測定）。
1 ボイスは 2 オペレータまたは 4 オペレータで構成されるので、1 ボイスでも予算を使い切る可能性があります。
このため、RP2040 では FM 音源部の整数化が必須です。

RP2350 の FPU は単精度だけです。
倍精度の部分は、RP2350 でもソフトウェア実装になります。

## 書き換えの方針

1. 正弦波は整数のテーブル参照にする。指数と対数のテーブルを使う OPL 系の方式にすれば、乗算はテーブル参照と加算で済む
2. 位相、エンベロープ、音量を整数（固定小数点）にする
3. 起動時に計算していた値（`pow`、`log2`、`exp`）は、テーブルにするか、整数の近似式にする
4. `std::vector` と `std::string` をやめ、固定長のアリーナにする
5. イベント列は曲の読み込み時に全展開せず、再生位置に合わせて順に復号する
6. 同時発音数を 32 から減らす。最初は 8 で試し、音を聴いて決める

上流の音色の再現（音色パッチ、エンベロープ、演算子の接続方式）は、この書き換えでも守ります。
音は上流とビット一致しません。
音の差は、ロースペックによる味として許容する方針です。

## 固定小数点版 FM コアの試作結果

`src/ma_fm_fixed.cpp` は、`ma_fm_core` の音源部（オペレータ、エンベロープ、8 種類の接続方式、LFO、KSL と KSR）を整数だけで書き直したものです。
浮動小数点、libm、ヒープは使いません。
テーブルは `tools/gen_fm_tables.py` が生成し、`src/ma_fm_tables.inc` に出力します。

`tools/fm_compare.cpp`（CMake のターゲット `fm-compare`）が、同じ音色と音程を両方のコアで鳴らして比べます。
サンプルレートは 22,050 Hz、鳴らす時間は 1.5 秒です。
波形をそのまま比べると、周波数のごく小さな差が位相のずれとして積み重なるので、ラウドネス包絡と対数スペクトルで比べています。

### 測定条件

- 測定日：2026-09-29
- 比較の対象：上流の `ma_fm_core` と `ma_fm_fixed`（GM 近似音色、ドラム近似音色、4 オペレータの全接続方式、波形 0 から 7）の 40 ケース
- 実行環境：x86-64 上のホスト実行。RP2040 実機ではない

### 結果

| 項目 | 結果 |
|---|---|
| ピッチテーブルの誤差 | 最大 0.044 セント |
| ラウドネス包絡の差（10 ms ごと） | 最大 0.37 dB、平均 0.01 dB |
| 音量のピークの差 | 最大 0.04 dB |
| 対数スペクトル距離 | 平均 0.70 dB、最大 4.78 dB |
| 立ち上がり 2,048 サンプルの SNR | 多くのケースで 35 から 50 dB |

対数スペクトル距離が大きかったのは、波形 3（四分の一正弦波）を使う 3 ケースです（`gm96-c4`、`wave3`、`fourop-algo0`）。
この波形は不連続なので、周波数のごく小さな差が波形の差として大きく出ます。
この 3 ケースの原因は、波形の形状から推測したもので、個別には検証していません。

### RP2040（Cortex-M0+）向けのビルド

`arm-none-eabi-g++ 9.2.1`、`-Os -mfloat-abi=soft` で `ma_fm_fixed.cpp` だけをコンパイルした結果です。

| 項目 | 結果 |
|---|---|
| text（テーブルを含む） | 9,182 バイト |
| data と bss | 0 バイト |
| 浮動小数点関数と libm への参照 | なし |
| 64 ビット演算の補助関数（`__aeabi_lmul` など） | `configure`、`noteOn`、`setPitch` の中だけ。1 サンプルごとの `tick` には無い |

`memcpy` への参照が残っています。`noteOn` の中で、音色パッチを構造体ごとコピーしているためです。

### この試作でまだ使っている上流の部分

- 音色の型 `FmVoicePatch` は上流のものを使っています。この型には `float panDefault` があり、`std::array` も含みます。固定小数点版の音源部は、これらを読みません
- 音色を選ぶ処理（`gmApprox`、`drumApprox`）は上流のものを、比較のために使っています

## 確認できていないこと

- RP2040 実機での動作と負荷は確認していません
- 音は聴いて確認していません。数値の比較だけです。手元に `.mmf` のテストデータが無く、上流の `smaf-render` の出力も聴いていません
- リンク後のコードサイズは測っていません。固定小数点版が 1 サンプルに使うサイクル数も、実機では測っていません

## 決める必要があること

- 出力のサンプルレート（22,050 Hz か、それより低いか）
- 同時発音数の上限
- 上流の PCM ボイス（ADPCM 再生）を RP2040 に載せるか。RAM の使用量が大きく変わる
